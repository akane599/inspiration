## Feature modules (Phase 5)

Every feature follows the same MVI shape (H5): a pinned `XxxDependencies` interface (the only thing it sees of the app; `AppContainer` implements all five), an Activity-scoped `XxxViewModel` with `state: StateFlow<XxxState>`, `onIntent(XxxIntent)` and one-shot `effects`, a stateless `XxxScreen(state, onIntent)`, and an `XxxRoute(deps, modifier)` entry point. State uses `ImmutableList` collections and `val`-only data classes. The Route sends `Visible` / `Hidden` from `LifecycleStartEffect { onStopOrDispose }` (start/stop and tab leaving composition), so the ViewModel only reads from the device between the two (H13); only Cockpit and Health poll (`liveReadings`), and only while visible. Mappers (`*Mappers.kt`, `XRayMapper.kt`, `ToolkitMapper.kt`) are pure and JVM-tested; screens carry screenshot previews in `src/screenshotTest` (light, dark, fontScale 1.5, 360/840 dp, empty, error). Number text goes through `TelemetryFormat`; strings are en+tr in each module's `res/values*/strings.xml`.

## Toolkit write path (Phase 5)

Features see only `ToolkitActions` (H12), never `ToolkitGateway`. Layers, top down:

1. [`ToolkitActions`](../../core/telemetry-engine/src/main/kotlin/com/akane/inspiration/telemetry/toolkit/ToolkitActions.kt) (production constructor `(gateway, store, holdBinding, nowMs)`; the `ToolkitBackend`/audit constructor is internal so a feature cannot skip confirmation or the audit log). One mutex serialises audit/state transitions; dexopt admission runs outside it with its PENDING row protected. API: `appState`, `dozeState`, `history`, `activeOverrides()`, `plan`, `planRestore(actionId)`, `execute(action, confirmed)`, `restore(actionId, confirmed)`, `resetAll()`, `reconcile()`, `startBgDexopt`/`cancelBgDexopt`/`bgDexoptStatus()`. Typed models in [`ToolkitModels.kt`](../../core/telemetry-engine/src/main/kotlin/com/akane/inspiration/telemetry/toolkit/ToolkitModels.kt) (`ToolkitAction`, `ToolkitPlan`, `ToolkitOutcome`, `ToolkitWarning`/`ToolkitRefusal`/`ToolkitUnavailable` enums whose wording the UI owns, `Override`, `ResetItem`, `BgDexoptStatus`).
2. Every write inserts a PENDING `toolkit_action` audit row before the privileged call, then finalizes it with the service's own before/after (DONE, FAILED, REFUSED, RESTORED, CANCELLED); once the row exists the write, its settlement and the RESTORED update run `NonCancellable`. Reads (plan, `appState`, overrides) always go to the service; the audit log is history, not state.
3. **Chain-original rule.** Chain membership is derived from each row's observed before/after, not its status: a FAILED row that moved its target to a third value is a chain link, and a same-value write is not a link and hides nothing. `chainOriginal(row, rows)` walks older linked rows of the same target (`targetKey`) while each one's `after` equals the next one's `before` (app-op `allow` and `default` are distinct states since F-01; a recorded legacy `default` original restores as `allow`), stopping at a completed restore or a gap. Exception: a completed 0.2.2 restore that wrote `default` stays an override while the live mode is still `default` (`legacyDefaultRestore`). Doze chains whose after-value is unset still count, so a custom original replaced via Balanced then Standard restores (F-06). A failed restore that observably moved the target is not a completed restore: its typed persisted intended value anchors the original even when its prior history was pruned or its confirmed before-value was external. `restore` and `resetAll` both put a target back to the value before the FIRST change of its chain, and a target already at that value is refused `ALREADY_RESTORED` (nothing written) and is not an active override. `activeOverrides()` lists exactly the changes read-back still shows in effect.
4. **Read-back.** `verify(action)` re-reads app ops / bucket / doze after a write; `reconcile()` finalizes rows left PENDING by a crash (DONE if the state matches, FAILED only on a mismatch or a conclusive refusal such as NOT_INSTALLED/DENY_*, left PENDING when the service is unreachable or the read is inconclusive). A matching or mismatching read-back is credited to the write only within 60 s of it (B-01); a later one settles the row FAILED/`UNVERIFIED` with no `after`. A write whose outcome is unknown (timeout after issue, failed read-back, failed doze rollback) comes back as service code `ToolkitCode.UNVERIFIED`; the row stays PENDING and the caller gets `Unavailable(ToolkitUnavailable.UNVERIFIED)`. `execute`/`restore`/`resetAll`/`activeOverrides` reconcile PENDING rows first, and `run()` refuses to write on top of a same-target row that is still PENDING. `AppContainer.start()` calls it on every transition to Shizuku Ready. Client-only result codes (`ToolkitClientCode`: NOT_CONFIRMED 100 … WRITE_ERROR 105) sit above the service's `ToolkitCode` range.
5. [`ToolkitGateway`](../../core/telemetry-engine/src/main/kotlin/com/akane/inspiration/telemetry/toolkit/ToolkitGateway.kt) maps the AIDL calls (`withTelemetryService`) into `GatewayReply`.
6. [`ToolkitExecutor`](../../core/shizuku-ipc/src/main/kotlin/com/akane/inspiration/ipc/toolkit/ToolkitExecutor.kt) in the shell-UID `TelemetryUserService`: one write lock; a shared `gate()` that refuses package reads/writes/plans with `UNSUPPORTED_USER` (14) when the app's user (`toolkitUserId(appUid)`) is not 0 (F-05); package regex (`matchEntire`), user-0 install check, hard-deny rules, a writable-mode check (`AppOpMode.DEFAULT` is never written; permissive writes use `ALLOW` = 3); then a fixed argv with absolute `/system/bin/cmd` and `--user 0`. The protected-package set (eight process spawns) is cached for reads for `PROTECTED_TTL_MS` (30 s) under the write lock and cleared by every write; a truncated or failed protected-package read fails closed. Helpers: `Toolkit.kt` (enums as explicit int codes, `PackageNames`, `DozeRaw`), `ToolkitParsers.kt`, `Inspection.kt`, `CommandRunner.kt`, `BgDexoptController.kt` (cancel argv per API level; with no cancel argv below API 33 it refuses start and cancel as `UNSUPPORTED_API`, N-03). Protected apps get lift-only writes; a protected package read returns its value with the refusal (`ToolkitResult.protectedRead`, N-06). No generic runner, no `sh -c`. Before changing a Doze profile, the executor requires the original raw value to be replayable by a fresh instance (`DozeRaw.isRestorable`); its process-local read-back memory is not sufficient restore evidence.
7. Persistence: `ToolkitActionDao` / `ToolkitActionEntity` in `:core:database` (newest-N and by-status queries, insert-and-prune, settled-row delete), exposed on `SnapshotStore` as `insertToolkitAction`, `updateToolkitAction`, `toolkitActions`, `pendingToolkitActions`, `deleteToolkitActions`. `kind` strings and `RETAINED_ROWS = 500` live in `ToolkitAuditLog` (`ToolkitModels.kt`). Override recompute reads only chains that may still be active (`mayBeActive` skips closed ones), and `pruneClosedChains` deletes closed chain prefixes older than the newest 500 rows without changing any `chainOriginal` answer.
8. **Dexopt lifetime.** Admission calls run outside the client mutex while `dexoptStartsInFlight` protects their PENDING rows from status/cancel/reconcile settlement; non-running service status remains Unknown until admission completes. Settlement and local-ID cleanup run `NonCancellable`. The hold supervisor retries/logs audit-read exceptions rather than dying, and releases the binding by its monotonic 60-minute cap plus 2-minute margin even without a UI collector.
